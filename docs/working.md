## Lessons Learned

- 2026-11-06: A Zoom dropdown's option list stays visible for about 300 ms after an option is picked. Waiting for the next list's option is not enough when two lists share option names (duration hours and minutes both offer "0"); wait for the previous list to close before opening the next one. Slowed-down demo runs hide such races, so verify writes at full speed too.
- 2026-10-31: The schedule form's save endpoint, `/rest/meeting/save`, contains none of the recording guard's mutation words, so the recording guard alone would have let it through. Meeting commands need their own deny-by-default rule for non-GET requests under `/meeting` and `/rest/meeting`.
- 2026-10-31: Capture a write's request with the request aborted before writing its permit; a permit written from the UI's appearance would have been wrong (`2:30` on screen, `02:30` in the body). A strict permit turns such a surprise into a refused, harmless save.
- 2026-10-31: Zoom's comboboxes swap elements after interaction (input to text span), the time-zone input's accessible name comes from `aria-labelledby` ("Time Zone") rather than its `aria-label`, options become visible a moment after they exist, and the duration minutes field only keeps a clicked option. Query controls by `[role=combobox][aria-label=...]` each time, read `value` or `innerText`, and wait for visibility and readback instead of sleeping.
- The recordings page ignores date-range query parameters in its URL and defaults to the last 365 days. The range lives only in the form body of `POST /nws/recording/1.0/host-list` (`from`/`to` as MM/DD/YYYY, `p`, `search_value`); rewriting those fields on the page's own request works for any range, including years back.
- The page's API calls carry an authorization header taken from page globals. Do not replicate the calls from outside the page; let the page make them and only rewrite form fields or read responses.
- Signed download links from the batch-download response return 403 unless the request carries both a `Referer` from the Zoom web origin and the browser session's cookies. A plain HTTP client with the right `Referer` still gets 403. Fetch the bytes through the browser context's request API, in ranges.
- Do not let the guard block static assets. The app ships JavaScript and CSS for its delete and trash dialogs (file names contain "trash" and "delete"); aborting them stops the recordings list from loading at all. The guard only considers API and document requests.
- The detail page's per-file download icons are hidden until hover and are not reliably clickable; the per-clip Download button plus its confirmation dialog ("Download recording files") is stable. Its accessible label is "Download " + the clip name, which is "Recording 1", "Recording 2" for multi-clip meetings but plain "Recording" on some single-clip meetings (and owners can rename clips), so match the visible text "Download" and the clip's position instead of a fixed label. The dialog does not appear once the user ticked "Do not remind me again", so the confirmation step is optional.
- When the batch-download response is intercepted, return an empty file list to the page; otherwise Chrome starts its own downloads of every file into the user's Downloads folder.
- 2026-10-24: `browser` rejected an older profile inside a Git repository, even though the directory was ignored. Launching with a fixed external profile (`~/.zoom-recording/browser-profile`) and having the human sign in yielded `browser_verified: true` and `signed_in: true` from `status`. Replace stale profile overrides; do not copy cookies/storage or weaken the own-browser check. Persisted state does not guarantee permanent authentication: recheck `status` and ask for human sign-in in the same profile when needed, without assuming a fixed session lifetime.
- 2026-10-24: Downloading and sharing use separate endpoints. `show` returns file metadata; `settings` now reads `share-data` and explicit Share/More settings controls. Canonical share URLs are requested output, unlike secret signed download URLs. Share-data responses can issue different share tokens on successive reads, so return the latest URL and compare settings rather than token equality. Passcode removal requires the exact one-shot `save-share-setting` payload and fresh readback; all other settings remain a human handoff.
- 2026-10-24: Zoom's checkbox decoration can intercept native-input clicks. Validate the Passcode input and its parent wrapper before clicking the wrapper; never use force clicks. Disabling Passcode can remove the invitee-bypass child checkbox, so avoid fixed checkbox counts or indices. Allow only named child disappearance with an unchanged `allowInviteesBypassPasscode` server flag; still reject loss or drift of any independent permission control.
- 2026-10-24: Network save success is not the panel's UI-settled signal. Wait for the current Save control to hide and More settings to reappear before readback; do not confuse an immediate stale checkbox with a failed server save, or retry a mutation to compensate.
